## Phase Goal

**As a** researcher, **I want to** open the live Findings app, sign in with an emailed 6-digit code or the demo password, stay signed in across refreshes, and sign out, **so that** I can reach my matches and connections securely.

This plan's slice: the demo account signs in with a password and every signed-in user sees their own database record, protected by the full schema and RLS.

## Planner Assumptions

- PA-03: Demo account is created once in the Supabase dashboard (Add user, Auto Confirm) rather than by a secret-key script; its credentials live only in the user's password manager and the gitignored `scripts/local.toml` used by `scripts/check_live.py`.
- PA-06: The keep-alive cron reads a dedicated `keepalive` table (one row, anon select policy) instead of exposing `profiles` to anon (CLAUDE.md / STACK.md section 7).
- PA-09: Schema follows ROADMAP Phase 1 notes over the research sketch where they differ: four give/need columns (`offers`, `needs`, `contributable_skills`, `want_to_learn`), real user-editable boolean toggles `seeking_mentor` / `open_to_mentoring` (PROF-03 needs overrides, so they are not generated columns), `methods_suggested` + `methods_override` with generated `methods_effective`. `match_profiles`, `my_connections` and the synthetic auto-accept trigger are left to Phases 4-5 (not listed in the Phase 1 notes).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon (publishable key) -> PostgREST | Anyone on the internet holding the public key |
| authenticated user -> PostgREST | User JWT; RLS and column grants decide reach |
| security-definer functions -> private tables | Only get_contact_email and the auth triggers may read/write profile_contacts |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-08 | Info disclosure | contact email | critical | mitigate | Email only in public.profile_contacts (RLS on, zero policies, privileges revoked); readable only via get_contact_email gated on self or an accepted connection; probes A3, D6, D7, D8 |
| T-01-09 | Tampering | public.profiles writes | high | mitigate | Update policy id = auth.uid() and is_synthetic = false; column-level update grants exclude id, is_synthetic, created_at; probes D4, D5 |
| T-01-10 | Tampering | public.connections status | high | mitigate | Recipient-only update policy, update grant on status only, guard_connection_update trigger enforcing pending -> accepted/declined and immutable parties/note |
| T-01-11 | Elevation of privilege | security-definer functions | high | mitigate | set search_path = '' and fully-qualified names on handle_new_user, handle_deleted_user, get_contact_email; execute revoked from public and anon |
| T-01-12 | Info disclosure | anon reads of profiles | medium | mitigate | No anon policy and privileges revoked on profiles; probe A2 |
| T-01-13 | Spoofing | demo account password | high | mitigate | Password only in the Supabase dashboard, the user's password manager and gitignored scripts/local.toml; demo user has ordinary RLS rights only |
| T-01-14 | Info disclosure | keepalive table | low | accept | Holds a single constant row with no user data; anon read is its purpose |
| T-01-SC | Tampering | pip installs | high | mitigate | No new packages in this plan; Plan 01 legitimacy gate and pins cover the environment |
</threat_model>
