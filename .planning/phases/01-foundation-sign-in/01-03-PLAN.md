## Phase Goal

**As a** researcher, **I want to** open the live Findings app, sign in with an emailed 6-digit code or the demo password, stay signed in across refreshes, and sign out, **so that** I can reach my matches and connections securely.

This plan's slice: the user stays signed in across a browser refresh, can sign out from any page, and never sees another session's identity.

## Planner Assumptions

- PA-04 (AUTH-04 cookie restore): only the Supabase refresh token is persisted, in a first-party cookie named `findings_rt` with `Path=/; Max-Age=604800; SameSite=Strict; Secure`. It is read once per Streamlit session from `st.context.cookies` (read-only in 1.65) and written/cleared by a tiny script rendered with `st.html(..., unsafe_allow_javascript=True)` (verified present in 1.65; not iframed, so `document.cookie` targets the app origin). No third-party cookie package, so no new install. Restore calls `sb.auth.refresh_session(token)` once; any AuthError (including "Invalid Refresh Token: Already Used") clears the cookie and shows Sign in. The client is created with `ClientOptions(auto_refresh_token=False)` so token rotation only happens inside app runs, where the cookie is re-synced.
- Fallback (assumption, recorded per orchestrator): if the cookie proves flaky on Streamlit Community Cloud during Plan 04 checks, first try `SameSite=Lax`; if still unreliable, record AUTH-04 as a known limitation in STATE.md Blockers/Concerns for the Phase 8 limitations document. The rest of the app does not depend on the cookie.
- PA-05: signed-in pages are Home and Account (both real pages); sign-out lives in the sidebar rendered by `app.py`, so it is on every signed-in page.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser cookie jar -> Streamlit server | Cookie value is attacker-controllable input on every new session |
| Streamlit server -> browser JS | Server-generated script writes the cookie; any embedded value must be inert |
| Streamlit process memory | One Python process serves every visitor; per-session state must not leak |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Info disclosure | findings_rt cookie (JS-readable refresh token) | high | mitigate | Only the refresh token is stored; Secure, SameSite=Strict, Path=/, 7-day Max-Age; tokens are single-use and rotate on every restore; cleared on sign-out; the app never renders user-supplied HTML, limiting XSS paths to the cookie |
| T-01-16 | Tampering | build_cookie_script / read_refresh_token | high | mitigate | Allowlist regex (letters, digits, _ - ., 8-512 chars) on read and write; value JSON-encoded; invalid values raise ValueError and are never embedded |
| T-01-17 | Denial of service | stale/reused refresh token | low | mitigate | Restore attempted once per session; any AuthError clears the cookie and shows Sign in instead of crashing |
| T-01-18 | Spoofing | shared computer after sign-out | medium | mitigate | sign_out revokes this session server-side (local scope), clears session state and the cookie, and restore is not re-attempted in the same session |
| T-01-24 | Spoofing / Info disclosure | per-session client regression (verification of the Plan 01 control for T-01-01) | critical | mitigate | AST scan test forbids cache decorators and stray create_client calls; two-session test proves distinct clients |
| T-01-SC | Tampering | pip installs | high | mitigate | No new packages: cookie handling uses Streamlit 1.65 built-ins instead of a third-party cookie component |
</threat_model>
