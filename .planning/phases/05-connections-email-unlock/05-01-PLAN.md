## Phase Goal

**As a** researcher, **I want to** send a connection request with a note from a match, a Discover card or a profile page, and have the recipient accept or decline it, **so that** we can exchange contact emails only once we have both agreed.

(This story restates the ROADMAP Phase 5 goal. That goal line is not written in user-story format.)

This plan's slice: the tracer goes from a profile page to a request, then to the recipient accepting, then to both emails on the Connections page. It then locks the database rules (synthetic auto-accept, insert columns, `my_connections`) and proves them live.

findings/services/connection_service.py (new, no streamlit; copy the AuthFailure wrapping style from auth_service.py):
- ConnectionFailure(Exception) carries user-safe text. NOTE_MAX = 500.
- send_request(sb, user_id, recipient_id, note) -> dict raises ConnectionFailure in three cases: user_id is empty ("Sign in again to send requests."), recipient_id equals user_id ("You can't send a request to yourself."), or the trimmed note is longer than NOTE_MAX ("Keep the note under 500 characters."). Otherwise it calls insert_request, then returns get_by_id for the new id, falling back to the inserted row. The re-read is required because the database may already have flipped a synthetic request to accepted after RETURNING (D-01). Any PostgrestAPIError (import it from supabase) or other exception becomes ConnectionFailure("Could not send the request. Try again in a moment.") from None. Log only the exception type and its code attribute. Plan 05-03 refines the codes.
- respond(sb, user_id, connection_id, accept) -> dict sets status accepted when accept is true, else declined, and calls set_status with user_id as recipient. Zero rows raise ConnectionFailure("Only the person who received this request can answer it.") (D-09). PostgrestAPIError (the guard trigger rejecting an answered row) raises ConnectionFailure("This request was already answered."). Otherwise it returns rows[0].
- list_connections(sb, user_id) -> dict with keys sent, received and accepted, built from list_mine. sent holds rows with direction sent and status pending or declined. received holds direction received with status pending. accepted holds status accepted in either direction. Keep the RPC order (newest first).
- connection_states(sb, user_id) -> dict keyed by other_id, each value holding state, connection_id and is_synthetic. pending plus sent maps to state sent, pending plus received to received, accepted to connected, declined to declined.

(b) D-01: create or replace function public.auto_accept_synthetic() returns trigger, language plpgsql, security definer, set search_path = ''. The body: if a public.profiles row with id = new.recipient_id and is_synthetic true exists, run update public.connections set status = 'accepted' where id = new.id and status = 'pending'. Then return null. The update runs as the function owner, who owns the table, the same way handle_new_user writes the contacts table, so RLS and the column grant don't block it. guard_connection_update still validates the transition and stamps responded_at. Then revoke execute on function public.auto_accept_synthetic() from public, anon, authenticated; drop trigger if exists auto_accept_synthetic on public.connections; and create trigger auto_accept_synthetic after insert on public.connections for each row execute function public.auto_accept_synthetic().
(c) D-03: create or replace function public.my_connections() returns table (connection_id uuid, direction text, status text, note text, created_at timestamptz, responded_at timestamptz, other_id uuid, other_name text, other_stage text, other_is_synthetic boolean, other_email text), language sql, stable, security definer, set search_path = ''.

  - direction is 'sent' when the caller is the requester, else 'received'.
  - other_name = coalesce(nullif(o.full_name, ''), 'Unnamed researcher').
  - other_email = case when c.status = 'accepted' then public.get_contact_email(o.id) end. The email must come only through get_contact_email; the function must not read the private contacts table itself.
